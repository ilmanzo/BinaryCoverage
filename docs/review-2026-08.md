# funkoverage code review — remediation plan (2026-08)

Working document. One section per item; each records its **Outcome** as work
lands. Deleted in the final commit of the branch (precedent: `745f3cf`).

Branch: `fix/review-2026-08`, cut from `main` at `d6d3423`.

## Context

A whole-repo review (design / performance / cleanliness) turned up 19 findings.
Three collide with decisions already taken and recorded in the
`fix/audit-2026-08` history — see **Rejected** below; they are documented here
so nobody re-derives them. The rest split into four groups:

1. **Two data-loss / host-integrity risks.** `install` can leave a system binary
   deleted if the shim copy fails partway through; `mergeLibraryDebugInfo`
   mutates live system shared libraries in place with `eu-unstrip`.
2. **Known unimplemented bugs** already documented in root `plan.md`
   (`enumerateOne` short-circuit, `ldd` fork-exec).
3. **Dead / write-only tracer state** and an always-nil error return.
4. **Report and enumeration performance.**

Intended outcome: `funkoverage install` never destroys a binary and never
mutates a system library; the two documented bugs are closed; report and
enumerate get measurably faster; the tracer sheds state nothing reads.

## Phase 1 — Correctness bugs

### C1 — `install` can leave the target binary gone **[e2e]**

`relocateOriginal` moves `/usr/bin/foo` into `SAFE_BIN_DIR`.
`enumerateAndPersist` rolls that move back on failure; `finishInstall` does not.
If `copyFile(shimBinary → realTarget)` fails — ENOSPC, read-only `/usr`,
truncated shim — `install` returns an error and `/usr/bin/foo` no longer exists.
`installMany` logs it and proceeds to the next binary.

**Change:** one `defer` in `install`, armed right after `relocateOriginal`
succeeds and disarmed once `finishInstall` returns; drop the ad-hoc rollback
inside `enumerateAndPersist` and the comment explaining why it was one-sided.

**Outcome:** done. `rollbackInstall` also restores in-place-unstripped system
libraries, clears the sidecars keyed on `safePath`, and drops the multicall
alias — the old one-sided rollback did none of those. A rollback that itself
fails is reported as CRITICAL on stderr rather than folded into the returned
error, which `installMany` would otherwise print as one more line in a list.
`installMulticallSymlink` now returns the link it created so the rollback can
remove it. `relocateOriginal` keeps its own internal rollback: it runs before
`install` has anything to disarm.

Test injection point: `findShimBinary` only `os.Stat`s its candidates, so
pointing `FUNKOVERAGE_SHIM` at a *directory* is accepted and then fails inside
`copyFile`'s `io.Copy` with EISDIR — exactly the target window, and behaves the
same as root or not (unlike an unreadable file).

### C2 — `uninstall` leaks sidecars

Removes `.funcs.json` and `.libbackup.json`, never `.filter.json` or
`.shimbin.json`. AGENTS.md says uninstall "removes sidecars".

**Change:** `WriteFilterSidecar(safePath, FilterSidecar{})` +
`WriteShimBinary(safePath, "")` — both delete the file on an empty value via
`writeJSON`.

**Outcome:** done, as `clearSidecars(safePath)`, shared by `uninstall` and by
C1's `rollbackInstall`. The library-backup sidecar stays out of it:
`restoreLibraryBackups` owns that one and has to put the libraries back before
the record of where their backups live is discarded.

Found by the `assertSafeBinDirEmpty` helper added for C1 — `.shimbin.json` was
the survivor in `TestInstallUninstall`. `.filter.json` only leaks when a filter
was actually set, which no existing test did.

### C3 — `enumerateOne` short-circuits on a sparse own-symtab

Root `plan.md` §3, confirmed repro: `_bz2.cpython-313*.so` exports one symbol
from its own `.dynsym`, so the first check returns 1 and returns immediately;
its debug file's `.symtab` has 18 real functions never consulted.

**Change:** prefer the external debug file's `.symtab` when one exists; fall
back to the main file's own only when none is found.

**Outcome:** done. The superset premise was checked on the VM across seven
images before the reorder, counting *defined* functions only (`FUNC`, `Ndx !=
UND`, non-zero size — what `SymtabFunctions` keeps). Zero runtime-only symbols
anywhere, so the reorder cannot lose anything:

| image | runtime | debug | runtime-only |
|---|---|---|---|
| `libgmp.so.10.5.0` | 874 | 997 | 0 |
| `libcrypto.so.3` | 5859 | 13101 | 0 |
| `libssl.so.3` | 603 | 2512 | 0 |
| `gzip` | 99 | 99 | 0 |
| `bzip2` | 39 | 39 | 0 |
| `squid` | 15174 | 15174 | 0 |
| `_bz2.cpython-313` | 1 | 19 | 0 |

`_bz2` reproduces root `plan.md` §3 exactly: 1 defined function in the runtime
file against 19 in its debug file. `libssl` is the biggest single win, 603 →
2512. Images with no debug file (`libz`, `libc` on this host) are unaffected —
`externalDebugPath` returns "" and the runtime symtab is used as before.

Test reuses the existing `buildStrippedLibFixture` (public symbol in `.dynsym`,
`static` one only in the `.debug` file), which is the same shape D1 needs.
Verified it fails without the reorder: `got [lib_public_func]`, missing
`lib_local_func`.

`externalDebugPath` is now called unconditionally, one extra `elf.Open` per
image: `BenchmarkEnumerateFunctions` 6 523 991 → 6 688 722 ns/op (+2.5%). P4
repays it.

Root `plan.md` §3 is pruned down to the one part C3 does *not* close: the
openQA `coverage_setup.pm` gap, which is in a different repo.

**Follow-up — C3 amplified a pre-existing whole-image-drop hazard.** Caught
only by the Leap 16 container run, which no other verification step covers:
`openssl` went from main's `1824 / 7186` to `181 / 16273`. The denominator was
C3 working as intended; the numerator was every `libcrypto`/`libssl` uprobe
being dropped.

Cause: `UprobeMulti` resolves the whole name batch up front and fails the call
on the *first* miss, so one unresolvable name costs the entire image. On Leap
16 the install-time `eu-unstrip` merge is refused (`cannot find matching
section for [10] '.rela.dyn'`), so the debug-only names C3 now prefers are
simply not in the file the kernel maps. Before C3 the runtime file's own
symtab was used whenever it was non-empty, which accidentally kept the batch
resolvable. The hazard itself is not new — `tests/e2e/test_gmp.sh`'s header
already documents it.

Fix: `attachableSymbols` (`cmd/shim_binary/tracer.go`) pre-filters each image's
batch against `funkutil.ResolvableFuncNames`, keeping each survivor paired with
the cookie `flattenFuncs` assigned it. `ResolvableFuncNames` deliberately
mirrors cilium's own predicate (`STT_FUNC`, `Value != 0`, `.symtab` ∪
`.dynsym`) because that is the cache `UprobeMulti` consults. Where the merge
succeeds nothing is filtered; where it fails coverage degrades to the unmerged
result instead of vanishing.

Result — Leap 16 `openssl` `1824 / 16273`: the called count matches main
exactly while keeping C3's richer denominator. Tumbleweed unchanged at
`3969 / 16297`. Both container suites green (9/9 each).

D1 subsumes this: attaching debug-only symbols by address removes the reason
the names are unresolvable. Keep the filter anyway — it is the safety net for
any image D1 declines to handle.

### C4 — `ldd` runs the target's own interpreter, as root

`ldd` invokes the binary's `PT_INTERP` with `LD_TRACE_LOADED_OBJECTS=1`, and
`install` runs as root. Root `plan.md` §2 wants this gone for fork-exec cost;
the privilege angle is the stronger reason.

**Change:** `DT_NEEDED` via `debug/elf`'s `ImportedLibraries()`, resolved
against `/etc/ld.so.cache` (parsed directly), honouring `DT_RUNPATH`/`DT_RPATH`
with `$ORIGIN`. Keep `ParseLddLibraries` as the fallback.

**Outcome:** done, in a new `cmd/libdeps.go` that also absorbs
`ParseLddLibraries` so all dependency resolution lives in one file.
`resolveLibraries` runs `dtNeededClosure` and falls back to `ldd` on any
unresolved SONAME, so a host the walk does not understand keeps today's exact
behaviour rather than silently losing libraries. `EnumerateFunctions` is the
only caller. `BenchmarkEnumerateFunctions` 6.52 ms → 4.25 ms (−35 %).

Two rules were missed by the original design and only surfaced because the
test diffs the resolver against `ldd` over 60 real host binaries:

- **`glibc-hwcaps` is not optional.** ld.so tries
  `<dir>/glibc-hwcaps/<level>/<soname>` before `<dir>/<soname>`, and openSUSE
  ships v3 builds of libz, libzstd, libjpeg, liblz4, brotli and ~40 more. The
  first cut resolved `libjpeg.so.8` to `/usr/lib64/libjpeg.so.8` while the
  process maps the v3 file — and a uprobe on the wrong inode never fires, so
  the library would have reported 0 % with no error anywhere. Handled by
  probing the supported levels per directory (`findInDir`) and rejecting cache
  entries under an unsupported level (`hwcapsUsable`). Which levels are
  supported comes from `golang.org/x/sys/cpu`, already a dependency.
- **`$ORIGIN` is relative to the realpath**, not to the path as given.
  `/usr/bin/androiddeployqt6` is a symlink into `/usr/lib64/qt6/bin`, and its
  `RUNPATH` of `$ORIGIN/../../` means the qt6 tree.

The ld.so.cache parser only handles the new format (`glibc-ld.so.cache1.1`);
the pre-2000 format falls through to the default directories and then to
`ldd`. Cache entries are ordered by ldconfig, and among those surviving the
hwcaps filter the first of the right ELF class/machine wins — glibc scores the
rest by legacy hwcap bits, which in practice only separates alternative
implementations of one SONAME (`zlib-ng-compat`'s `libz.so.1` against the
stock one). Marked `ponytail:`.

Verified: 319/319 host binaries produce a dependency set identical to `ldd`'s
after `canonicalPath`, with zero fallbacks. The remaining spelling differences
(`/lib64` against `/usr/lib64`, uncleaned `$ORIGIN/../..`) are the same
physical files, which is what `EnumerateFunctions` keys on.

Closes root `plan.md` §2 — delete that section in the final commit.

## Phase 2 — Stop mutating system shared libraries **[e2e]**

### D1 — Attach library uprobes by address instead of by merged-in-place name

**The problem.** `mergeLibraryDebugInfo` runs `eu-unstrip` over
`/lib64/libfoo.so.N` on the live host, because uprobe attach resolves symbol
names against the exact file the kernel maps and a library's local functions
live only in its external debuginfo. So: `rpm -V` reports every touched library
as modified; a crash between backup and restore leaves the host permanently
modified; concurrent installs sharing a library race the backup.

**The replacement.** `link.UprobeMultiOptions.Addresses` accepts pre-resolved
file offsets and is mutually exclusive with `symbols`, bypassing name
resolution. cilium computes offsets as
`sym.Value - prog.Vaddr + prog.Off` over `PT_LOAD | PF_X`. We compute the same:
symbol **vaddrs** from the debug file, **program headers** from the real
runtime library.

**Verified on the VM** (libgmp 10.5.0), read-only, before writing code:

| check | result |
|---|---|
| exec `PT_LOAD` vaddr/memsz identical in both files | ✅ `0x12000` / `0x7e4a9` |
| build-id identical in both files | ✅ `cbd15edf…3ba464` |
| internal symbols absent from the runtime file | ✅ `mpn_fft_initl` @ `0x34160` only in debug `.symtab` |
| computed offset lands on an instruction boundary | ✅ `objdump -d` at `0x34160` → clean prologue |
| debug `.symtab` ⊇ runtime symbols | ✅ 1040 ⊇ 911, zero runtime-only; 129 gained |

> **The trap.** The two files agree on `p_vaddr` but **not** `p_offset`: the
> exec segment is at `0x12000` in the runtime library and `0x1000` in the debug
> file (allocated sections are `NOBITS`). Feeding the debug `*elf.File` to the
> conversion yields an offset 0x11000 too low — a uprobe landing
> mid-instruction. `SymbolFileOffsets` takes both files precisely because of
> this: **values from `debug`, program headers from `runtime`.**

**Scope.** Libraries only — `mergeDebugIfExternal` stays for the main binary
(our own relocated copy under `SAFE_BIN_DIR`, not a system file).

**Scope — per-symbol, not per-image.** C3 makes enumeration prefer the debug
symtab whenever one exists, so "this image came from a debug file" would be true
for nearly every system library and D1's blast radius would silently become
universal. Instead partition the accepted names at install time: present in the
runtime file's own symtab/dynsym → `Names` (attach by name, unchanged); found
only in the debug file → `Offsets` (attach by address). libgmp: 911 by name,
129 by address. Empty `Offsets` ⇒ exactly today's path.

**Mandatory safety guard.** A uprobe at a wrong address lands mid-instruction
and kills the target with SIGILL/SIGSEGV — strictly worse than today's "log and
skip". The sidecar records the library's GNU build-id alongside its offsets; the
shim re-reads it at attach time and skips the image on mismatch. No build-id ⇒
no address-based attach for that library.

**Migration.** An old `.funcs.json` deserialises with empty `Offsets` = "attach
by name" = pre-existing behaviour. No version field needed. **Uninstall of an
install made by the old code must still restore libraries** — keep
`ReadLibBackups` + the restore loop for one release, guarded on the sidecar
existing, then delete.

**Verification, in order:**

0. **Unit test first — e2e cannot catch a broken conversion.** Every image
   sampled on the VM (`libcrypto.so.3`, `libc.so.6`, `libstdc++.so.6`,
   `/usr/bin/bash`, `/usr/bin/gzip`, libgmp) has `p_offset == p_vaddr` on every
   `PT_LOAD`, so the conversion degenerates to the identity and a wrong
   implementation passes the whole sweep, then breaks elsewhere. Use cilium as
   an oracle: for every symbol in **both** symtabs, cilium resolves by name and
   `SymbolFileOffsets` by address — they must agree. 911 cross-checks on libgmp.
1. `test_gmp.sh` is the gate, plus `sha256sum /lib64/libgmp.so.10*` before and
   after asserting equality. Expect ~129 internal `mpn_*` newly traceable.
2. `rpm -V gmp` clean after install (today it is not).
3. `test_{nss,pam,nginx}_dlopen.sh` — the dlopen JIT path still attaches by name.
4. Full sweep.

**Fallback:** if address-based attach proves unreliable on some image class,
keep the name path and land only the build-id staleness guard plus an `O_EXCL`
backup write for `mergeLibraryDebugInfo`. Record the finding here rather than
deleting it.

**Outcome:** done, as designed, plus two hazards the plan did not foresee — both
found only by running it on real distro libraries, neither reachable from the
libgmp pair the design was drawn from.

`eu-unstrip` on system libraries is gone: `mergeLibraryDebugInfo`, `getBuildID`
and the `WriteLibBackups` call are deleted, `rollbackInstall` no longer restores
libraries, and `restoreLibraryBackups` survives only to clean up installs made by
0.8.3 (doc-commented for deletion one release after 0.8.4). `.funcs.json` now
carries `ImageFuncs{BuildID, Names, Offsets}` with an `UnmarshalJSON` that still
accepts the pre-0.8.4 bare array. The gate holds: `test_gmp.sh` rewritten to
assert `sha256sum` equality across the whole install/uninstall cycle passes with
libgmp **byte-identical**, `rpm -V` unchanged, and coverage identical to the
merge-based baseline (15/98).

**Hazard 1 — two unprobeable functions killed 7167.** `UprobeMulti` resolves the
whole batch up front and fails the entire call on the first bad entry, so
openssl dropped from 3971 to 2185 called: the x86 uprobe decoder refuses
`_aesni_ctr32_ghash_6x` and `_aesni_ctr32_6x` (hand-written AES-NI asm) with
`EOPNOTSUPP`, and took the other 7165 addresses down with them. Fixed with
`attachBisect` in `tracer.go` — attach the batch, and on error halve and recurse,
so a bad entry costs `log2(n)` retries instead of the image. openssl back to
3965/16216. The name path gets the same treatment for free.

**Hazard 2 — a distro debug file that is not the library's.** openSUSE Leap 16
ships `libopenssl3-debuginfo` built from a *different build* of libcrypto than
the one on disk: build-id `780e425a…` in `/usr/lib64/libcrypto.so.3.5.0`,
`b844407f…` in `/usr/lib/debug/…/libcrypto.so.3.5.0.debug`, exec segment memsz
`0x378869` vs `0x378b79`, and no `/usr/lib/debug/.build-id/78/…` entry at all.
Its symbol values describe other code, so `openssl version -a` died with SIGSEGV
— precisely the failure mode the "mandatory safety guard" paragraph above
predicts. (It is also why Leap 16's `eu-unstrip` used to fail with "cannot find
matching section for [10] '.rela.dyn'"; the old code failed safe by accident.)

The guard therefore lives one level lower than planned: `SymbolFileOffsets`
itself refuses to emit anything unless `BuildID(runtime) == BuildID(debug)`, so
no caller can express the dangerous pairing. Leap 16 falls back to name-only
attach automatically — 1824/7183, exactly `main`'s number — while Tumbleweed
keeps the address path. Verified that a well-formed pair is unaffected:
`objcopy --only-keep-debug` preserves note-section *contents* (binutils keeps
`SHT_NOTE` verbatim), so the debug file's build-id is real, not `NOBITS`.

The build-id is checked twice on purpose: here against the debug file at install
time, and in the shim against the mapped library at attach time (`attachPlan.verify`
drops the whole address batch on mismatch, leaving names).

**Coverage:** `internal/funkutil` 90.9 → 92.1, `cmd` 75.4 → 77.1,
`cmd/shim_binary` 25.3 → 30.8. The offset unit test needed a 300-export fixture
to be non-vacuous: with a small library the runtime and debug files place the
exec segment at the *same* `p_offset`, so swapping which file's headers the
conversion reads still passed. `assertDiscriminating` now fails the test if a
future fixture regresses to that.

**Full sweep** (VM host + both container images): green, all counts at baseline.

**E5 rejected, by the e2e test the plan itself nominated.** `max(len(refs)/2, 4096)`
was implemented and `test_nginx_dlopen.sh` failed on a missing
`ngx_http_echo_handler`: nginx's 3940 static functions bought 1970 dynamic slots,
and the shim exhausted them before reaching the echo module. The premise behind
scaling — "a plugin host's plugins are smaller than the host" — is wrong about
what the dlopen path actually instruments. It does not instrument the plugin; it
instruments *every* newly mapped non-noisy library the target pulls in, so the
reserve has to be sized for those, which has nothing to do with the target's own
function count. Reverted to the flat 100000, with the measurement recorded in the
constant's doc comment and a `ponytail:` note pointing at the real fix
(`BPF_MAP_TYPE_HASH`, which allocates on demand at the cost of a hot-path lookup
and a `tracer.bpf.c` change). The 800 KB stands until someone measures that it
matters.

## Phase 4 — Performance

| id | item | outcome |
|---|---|---|
| P1 | With `--formats html,txt,xml`, `splitCalledUncalled` (two allocations + two sorts) runs once per format per image and `summarizeCoverage` twice. Compute both once in `cmdReport`, thread through `emitReport` → `perImage`. | **done** — see below |
| P2 | `printTxtReport` uses `fmt.Printf` per line against unbuffered `os.Stdout` — one `write(2)` per function. Every other writer already goes through `writeBuffered`. | **done** — see below |
| P3 | `SymtabFunctions` demangles each symbol to evaluate `keep`, discards it, returns the raw name; `writeFunctionsLog` then demangles the whole set again. Return both forms. Folds into the D1 signature change. | _pending_ |
| P4 | Library enumeration is sequential — bottleneck **C.3** from `origin/issue-123`, the only item of that plan never implemented. `errgroup` with `SetLimit(GOMAXPROCS(0))`, same shape as `analyzeLogs`. | _pending_ |

**P1 as shipped.** `buildReportSet` (`cmd/report.go`) computes `summarizeCoverage`
plus the per-image split once — the split still runs under an `errgroup`, which
is where the concurrency that `perImage` used to provide now lives. `reportSet`
carries `Images []imageReport` and `Totals`, ordered identically, and
`emitReport`/`perImage`/the three generators consume it instead of the coverage
map. The generators no longer see `*CoverageData` at all: `len(Called) +
len(Uncalled)` is `len(TotalFunctions)` by construction, since the split
partitions exactly that set.

Two hazards the change created, both covered by new tests:

- `generateAggregateHTMLReport` rewrites each row's `ImageName` to its base
  name. That was safe when it owned a fresh `summarizeCoverage` result; sharing
  one `CoverageTotals` across formats made it corrupt txt/xml output, which
  print full paths. It now clones `Rows` first
  (`TestGenerateAggregateHTMLReport_DoesNotMutateSharedRows`).
- `printTxtReport` pairs `Images[i]` with `Totals.Rows[i]` positionally
  (`TestBuildReportSet` asserts the two orders match, and that a name present
  only in `CalledFunctions` stays out of the split).

Measured on the two-format path, which is what the item is about — the existing
single-format benchmarks cannot show it, because with one format there is
nothing to share. New `BenchmarkEmitReportMultiFormat`, `-benchtime 20x
-count 3`, against the same benchmark added to a `git archive` of the parent
commit: **8.0 / 8.8 / 8.9 ms → 7.4 / 7.3 / 7.6 ms**, roughly 14% off. No other
benchmark moved outside noise (ScanLog 3.21→3.31, AnalyzeLogs 16.0→17.3,
GenerateHTMLReport 20.9→20.3, GenerateXUnitReport 5.27→5.02, EmitReportHTML
5.38→5.20, EmitReportXML 2.24→2.04, EnumerateFunctions 4.36→4.32 ms). The
corpus is 200 images × 50 functions; the saving scales with the sorts, so a
real target like squid (13 628 functions) gains more than this.

**P2 as shipped.** `printTxtReport(out io.Writer, set reportSet)` wraps `out` in
a `bufio.Writer` and flushes on return; `emitReport` passes `os.Stdout`. Not
`writeBuffered` — that one creates a file, and this writes to a stream the
caller owns.

Measured by syscall count rather than by benchmark, since the cost is
`write(2)` against a terminal or pipe and `io.Discard` would hide it. A 5000
-function corpus, `report ... --formats txt`, stdout to `/dev/null`, under
`strace -c -e trace=write`: **5015 → 42 writes**. Output is byte-identical to
the parent commit's (`diff` clean). `TestPrintTxtReport` now writes to a
`bytes.Buffer` instead of swapping `os.Stdout` for a pipe, which also drops the
4096-byte read that would have silently truncated a longer report.

| id | change | outcome |

## Rejected — do not re-propose

Each was already investigated; re-raising costs someone the same afternoon twice.

**R1 — `findLibcPath`'s hardcoded path list.** The review proposed checking
`/proc/<pid>/maps` before the ten hardcoded libc/libdl paths, on the grounds
that uprobes match by inode and the hardcoded probes test the host filesystem
rather than the target's mount namespace. **The premise is wrong**, and it was
tried and reverted in `5f785fb` (audit item A4). `findLibcPath(rootPID)` is
called from `Tracer.Start` while `rootPID` is still the shim process itself —
blocked on the ready-pipe read, *before* `syscall.Exec` into the real target. At
that moment `/proc/rootPID/maps` shows the shim's own memory, and
`funkoverage-shim` is a statically linked Go binary that maps no libc at all.
Removing the hardcoded fallback disables the dlopen uretprobe on every host. The
issue #152 exec-in-place redesign did not change this timing.

**R2 — `generateXUnitReport`'s `TOTALS` block** as a duplicate of `summaryText`.
Rejected as audit item A10: `Message` and `Text` are separate XML fields
consumed independently by CI tooling and the maintainer wants both.
`TestGenerateXUnitReport` asserts on the TOTALS text explicitly.

**R3 — Removing the CLI aliases.** Done in `6d8e7a3` (audit item B4), then
deliberately reverted in favour of documenting them (`bb40b2d`). `helpText` now
lists every alias and explains why `-u` is absent. Settled.

**Deferred, not rejected — sidecar consolidation.** C2 brings the count of
`XPath`/`WriteX`/`ReadX` triplets to four, the threshold audit item A15 named
for revisiting a generic `sidecar[T]`. Phase 2 then deletes one
(`libbackup.go`), putting it back at three. Decide after Phase 2; out of scope
here.
